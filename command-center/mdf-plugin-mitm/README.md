# mdf-plugin-mitm

Per-instance mitmproxy supervisor for the MayaOS Device Farm.

## What it does

For each MDF emulator instance:

1. Operator clicks **Intercept On** in the MDF UI.
2. The plugin spawns a `mitmdump` process bound to a per-instance
   port (`8080 + index`). The MDF root CA is the mitmproxy CA — and
   it's already in the device's vendor trust store (baked at build
   time in `aosp-tree/vendor/mayaos/rootdir/system/etc/security/cacerts/`),
   so **no per-app cert install is needed**.
3. iptables NAT rules on the device push port 80/443 traffic through
   the mitm port. (The Android system proxy setting is unreliable;
   apps can ignore it. iptables is honored by every TCP socket.)
4. mitmdump's [addon script](lib/mitm-addon.py) streams each flow to
   `/run/mdf/mitm.sock` (Unix datagram). The plugin forwards each
   flow into the `mitm_flows` RethinkDB table, which the UI tails via
   a changefeed websocket.

## Wire format

See plan §11.4. Every flow is:

```json
{
  "id": "uuid",
  "serial": "emulator-5554",
  "ts": 1729900000000,
  "phase": "request",
  "method": "GET",
  "url": "https://...",
  "headers": { ... },
  "body_len": 1234
}
```

## Intercept rules

Operators can post JSON match-action pairs:

```json
POST /mdf/mitm/devices/emulator-5554/intercept-rule
{
  "when":   "response",
  "match":  { "host": "api.example.com", "path": "/v1/me" },
  "action": { "set_status": 401, "replace_body": "{}" }
}
```

The plugin SIGHUPs the per-instance mitmdump, which reloads the rule
file and starts applying.

## CA generation

The MDF root CA is generated by `scripts/gen-mdf-root-ca.sh` and lives
in Vault at `secret/mdf/ca`. The mitmdump container fetches the cert +
key on startup, writes them to `~/.mitmproxy/`, and starts as the
mitm CA without re-generating. See plan §5.2.

## Tables

- `mitm_sessions` — `{serial, port, startedAt, status}`
- `mitm_flows`    — `{id, serial, ts, phase, method, url, headers, body_len}`
- `mitm_rules`    — `{serial, when, match, action, ts}`
