# MayaOS build runbook

Operational notes for running the AOSP 16 (`android-16.0.0_r4`) MayaOS build
pipeline on RunPod. Most of this document is the result of failures observed
in production; treat each section as a "don't do that again" reminder rather
than nice-to-have advice.

The build pipeline itself is described in [`architecture.md`](architecture.md);
this document is purely the **runtime / operational** counterpart.

## Pod sizing on RunPod

The builder is a single RunPod GPU pod (`mayaos-aosp-builder`). The GPU is
unused by the build itself — we lease GPU pods because they're the only SKU
on RunPod that consistently gives us enough RAM for AOSP.

| metric | host visible | cgroup quota | who is right |
|---|---|---|---|
| CPU | `nproc` = 128 | `cpu.max` = `1360000/100000us` (~13.6 cores) | **cgroup** |
| RAM | `free -h` = 503 GB | `memory.max` = ~57 GB | **cgroup** |
| Disk | host filesystem (~3 TB) | quota varies by pod plan | host |
| GPU | RTX A6000 | full — 1 GPU per pod | full |

The `RUNPOD_GPU_TYPE="NVIDIA RTX A6000"` SKU consistently gives ~57 GB
cgroup memory and ~13 cores CPU quota on the SECURE tier. **Do not trust
`free` or `nproc`** when computing build parallelism — both report the
shared host's totals, which on RunPod's A6000 hosts is roughly 8x the
quota actually granted to your container.

## OOM at ~30% — kotlinc heap × parallelism

**Symptom:** the build runs cleanly through Soong and the first ~28% of
ninja, then around the
`frameworks/base/libs/WindowManager/Shell/shared:WindowManager-Shell-shared-desktopMode`
target the log fills with:

```
fatal error: out of memory allocating heap arena metadata
external/kotlinc/bin/kotlinc: line 98: <pid> Segmentation fault
NN:NN:NN dump process tree failed with: exit status 254
panic: dump process tree failed with: exit status 254
#### failed to build some targets (HH:MM:SS (hh:mm:ss)) ####
BUILD_DONE_EXIT=2
```

**Root cause:** the default kotlinc heap is `-Xmx8192M` (set inside
`external/kotlinc/build.gradle.kts` and propagated to every Kotlin
compilation) and ninja's `-j` defaults to `nproc` (128 on this host).
With ~13 actual cores, ninja schedules 13 concurrent kotlin compilations
× 8 GB heap each = ~104 GB just for kotlinc, against a 57 GB cgroup
memory cap. The Go runtime backing soong's helpers fails first ("out of
memory allocating heap arena metadata") because Go demands a large
contiguous virtual arena and is unlucky enough to be the first to ask
once memory pressure ramps. Within a few seconds of that, kotlinc itself
gets `SIGSEGV` from the cgroup OOM-killer and the whole build dies.

**Fix:** cap both axes. The on-disk runner script
(`/workspace/run-mayaos-build.sh`, generated by
`runpod/start-tmux-build.sh`) honours two environment variables for this:

```bash
PARALLEL_JOBS_OVERRIDE=8 \
_JAVA_OPTIONS="-Xmx4g" \
bash /workspace/run-mayaos-build.sh
```

- `PARALLEL_JOBS_OVERRIDE=8` — overrides `detect_parallelism()`'s
  cgroup-derived value. The auto-detect already does the right thing on
  most hosts but on hosts where cgroup files are unreadable it falls
  back to `nproc` and OOMs.
- `_JAVA_OPTIONS=-Xmx4g` — caps every JVM the build launches
  (kotlinc, javac, d8, r8, signapk, …) to 4 GB heap. With `-j8` × 4 GB
  = 32 GB worst case, which fits comfortably under the 57 GB cgroup cap
  even with the rest of the build's working set.

The runner script bakes these in too — search for `_JAVA_OPTIONS=` and
`PARALLEL_JOBS_OVERRIDE=` in `runpod/start-tmux-build.sh`.

## R2 bucket scoping

The build's after-build hook (`pipeline/hooks/after-build.sh`) reads
`$R2_BUCKET` and aborts with a missing-env error if unset. The runner
script bakes the value in from the launcher's env at script-generation
time — **changing `.env` after the runner script is on disk does
nothing**. To migrate buckets:

1. Update `.env` (`R2_BUCKET=<new>`).
2. Either re-run `runpod/start-tmux-build.sh` (regenerates
   `/workspace/run-mayaos-build.sh`) **or** patch the on-disk script
   directly (`sed -i 's|R2_BUCKET=.[^.]*.|R2_BUCKET="<new>"|'
   /workspace/run-mayaos-build.sh`).
3. Confirm the credentials in `.env` actually have access to the new
   bucket. The R2 token is bucket-scoped — a token minted for
   `panditai-training` returns `AccessDenied` on `s3://android/` even
   though the keys themselves look fine. Test with:

   ```bash
   aws --endpoint-url=https://${R2_ACCOUNT_ID}.r2.cloudflarestorage.com \
       s3api head-bucket --bucket "$R2_BUCKET"
   ```

   If this returns `AccessDenied`, edit the token in the Cloudflare
   dashboard → R2 → Manage Tokens → expand the bucket scope, **or**
   mint a new token. Then retest before kicking off another 4-hour
   build that will only fail at the upload step.

The fleet-side watcher
(`scripts/fleet-console` ↔ `/root/mayaos-x86-watcher.sh` on the fleet
pod) has a safety gate (`ANDROID_CREDS_VERIFIED=1` in
`/etc/mdf/r2.env`) that you flip after verifying the new credentials
work, so the watcher refuses to poll until you've done the test above.

## Build resume

The `out/` tree (`/workspace/aosp-src/out`, ~350 GB at full build) is on
the network volume and survives pod stop/restart. Ninja's incremental
state lives in `out/.ninja_log` and `out/.ninja_deps`; soong's lives in
`out/soong/`. To resume a stopped build:

```bash
ssh root@<builder> 'cd /workspace/aosp-src && \
    PARALLEL_JOBS_OVERRIDE=8 _JAVA_OPTIONS=-Xmx4g \
    bash /workspace/run-mayaos-build.sh'
```

This skips repo sync (already set via `SKIP_SYNC=1` in the runner) and
ninja picks up where it left off. The previously-OOM'd targets
(WindowManager-Shell, AdServices, MediaProvider, SettingsLib, Telephony)
will be redone first (~5 min of CPU) before the build continues forward.

To start clean, `rm -rf /workspace/aosp-src/out` before launching.
This frees ~350 GB of network volume but adds ~4 hours to the next
build.

## inherit-product first-non-empty-wins gotcha

AOSP's `inherit-product` macro treats single-value variables
(`PRODUCT_BRAND`, `PRODUCT_MODEL`, `PRODUCT_MANUFACTURER`,
`PRODUCT_DEVICE`, `PRODUCT_NAME`) as "first non-empty wins". So if
`mayaos_emu_s26ultra_x86_64.mk` does:

```makefile
$(call inherit-product, $(SRC_TARGET_DIR)/product/sdk_phone64_x86_64.mk)
$(call inherit-product, vendor/mayaos/product.mk)
PRODUCT_BRAND := samsung   # too late if vendor/mayaos/product.mk also set it
```

…the upstream `sdk_phone64_x86_64.mk` body's `PRODUCT_BRAND := Android`
runs first, sets the var, and then **vendor/mayaos/product.mk's
`PRODUCT_BRAND := samsung` is silently dropped** because the var is
already non-empty. The post-build sysprop validator catches this as
`error: found duplicate sysprop assignments` for
`ro.product.vendor.brand`.

**Rule:** `PRODUCT_BRAND`, `PRODUCT_MODEL`, `PRODUCT_MANUFACTURER` must
be assigned in the leaf `.mk` body **after all `inherit-product` calls**.
This is what upstream itself does (see e.g. `aosp_arm64.mk`).

The two leaf MayaOS profile files
(`aosp-tree/device/mayaos/galaxy-s26-ultra/mayaos_emu_s26ultra{,_x86_64}.mk`)
already follow this rule, with a comment block in each explaining why
the assignments live where they do. **Do not move them up.**

## arm64-on-x86_64 host: blocked

The MayaOS arm64 emu/ bundle (`mayaos_emu_s26ultra-userdebug`) cannot
be launched on an x86_64 RunPod fleet pod, even with KVM accel disabled.

Two layers of failure:

1. **Emulator wrapper** (`emulator/emulator-headless`) hard-checks that
   the AVD ABI matches the host architecture and exits with
   `Mixing 32-bit and 64-bit binaries / cannot run binary file` when
   the host is x86_64 and the AVD is arm64-v8a. There's no flag to
   disable this check.

2. **Direct qemu invocation** (`qemu-system-aarch64-headless` with
   `-machine virt-7.2 -cpu cortex-a76 …`) gets past the wrapper but
   fails inside QEMU itself. The Android-fork `aarch64-ranchu` machine
   type (the only one the boot blob supports) does not have a PCI bus,
   yet the QEMU binary unconditionally configures a PCI-attached audio
   device (`hda` or `virtio-snd-pci`) regardless of `-no-audio` /
   `QEMU_AUDIO_DRV=none` / `-audiodev none`. The audio device lookup
   crashes with
   `qemu-system-aarch64-headless: -device hda: No 'PCI' bus found`.

   Patching this requires recompiling the Android QEMU fork, which is
   a multi-day effort and not worth it given the x86_64 path works.

**Workaround:** build the x86_64 profile
(`mayaos_emu_s26ultra_x86_64-userdebug`) instead. It runs natively on
the x86_64 fleet pod via the standard `emulator -avd <name>` path,
gets KVM acceleration where available, and TCG fallback otherwise.

## Fleet pod auto-termination

RunPod will terminate (not just stop, **delete**) GPU pods after long
periods of low utilization, and there is no warning. The fleet pod
holding STF, the watcher, and any running emulators went from
`RUNNING uptime=10h37m` to gone-from-inventory inside ~2 hours of
idle. Terminated means: the pod ID is permanent dead, the network
volume is detached, and any ephemeral state on the container disk
(STF db, /etc/mdf/r2.env, /root/launch-mayaos-x86.sh,
/root/mayaos-x86-watcher.sh) is gone.

**Mitigation:**

- Anything that must survive (STF rethinkdb data, MayaOS x86 bundle,
  watcher script, /etc/mdf/r2.env) lives on the network volume
  (`/workspace`), **not** the container disk.
- The fleet pod respawn flow is fully scripted — `make mdf-fleet-up`
  pulls a fresh runpod/base pod, mounts the same network volume, and
  re-runs the bootstrap that installs STF, the watcher, the x86
  launcher.
- The local fleet console (`scripts/fleet-console/`) detects pod IP
  changes via the `BUILDER_HOST` / `FLEET_HOST` env vars; restart
  `./start.sh` after a respawn and it re-tunnels.

## Stopping the builder

To pause without losing state:

```bash
RUNPOD_API_KEY=... curl -sS -X POST https://api.runpod.io/graphql \
    -H "Authorization: Bearer $RUNPOD_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{"query":"mutation { podStop(input:{podId:\"<id>\"}) { id desiredStatus } }"}'
```

`podStop` halts compute charges (`$0.49/hr` for A6000) but keeps the
network volume billed at ~$0.07/GB/month — for a 500 GB working set
that's ~$35/month. To free the storage, instead use
`podTerminate(input:{podId:\"<id>\"})` after backing up anything you
need (the MayaOS bundle should already be in R2 from the after-build
hook).

To resume from a stopped pod, the RunPod podResume mutation puts you
back on the same network volume with the same SSH credentials. The
ssh port may change — re-run the inventory query to find the new
`publicPort`.
